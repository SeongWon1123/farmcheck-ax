기준: 2026년 11월 7일 확인 결과. 발표 1명, 화면 조작 1명, 약 6분.

> 후속 연결 완료: 이 PC에서는 실제 녹차 기록과 실험 모델을 같은 화면에서
> 사용할 수 있다. 연결된 로컬 시연은 `docs/green-tea-connected-demo.md`를 따른다.
> 아래 대본은 공개 합성 화면과 실제 API를 나누어 보여주는 기존 구성이다.
> 공개 사이트가 새 로컬 연결과 같은 상태라는 뜻은 아니다.

## 시연의 중심 이야기

**“전체 점수는 99%인데, 특정 주차는 왜 절반 가까이 놓칠까요?”**

농업 AI 개발자가 녹차 생육 주차 모델을 추가 학습한 뒤, 전체 점수만으로
지나치기 쉬운 데이터·모델 문제를 찾아 검수 담당자에게 넘기는 상황이다.
작물 전체에 적용되는 완성 서비스를 주장하기보다 녹차 한 작물로 실제 흐름을 보여준다.

이번에 추가 학습한 것은 녹차 모델의 분류층이다. 다른 작물 모델은 추가 학습하지 않았다.
또한 이 실험에서 라벨을 고치지는 않았으므로 “검수해서 정확도를 높였다”는 이야기는 하지 않는다.

실제 불일치 8장이 공개 앱에 등록되어 있거나 새 서빙이 공개 앱에 연결됐다고 설명하지 않는다.
개발자용 데이터 검수 대시보드, 원클릭 학습, 검토 후 자동 재학습은 아직 없다.

**화면:** 보고서의 시험 결과 표. 99.23%와 1주차 재현율 57.89%를 함께 보여준다.

**발표자**

> “농업 AI 개발팀이 녹차 생육 주차 모델을 준비한다고 가정해 보겠습니다.
> 제공 라벨과 예측이 일치한 비율은 99.23%입니다.
> 그런데 1주차만 보면 19장 중 11장만 맞혔습니다.
> 전체 점수 하나로는 어떤 데이터를 다시 확인해야 하는지 알기 어렵습니다.
> 팜체크는 이런 확인 대상을 근거와 함께 남기고 다음 담당자에게 넘기는 데 초점을 맞춥니다.”

### 2. 학습 자료 점검 — 0:40~1:25

**화면:** 같은 보고서의 분할 표와 해석 범위. 필요하면 비공개 감사 보고서를 연다.

**발표자**

> “실제 녹차 사진과 JSON 3,872쌍을 확인했습니다.
> 9~11주차는 없고, 일부 주차에 사진이 몰려 있습니다.
> 사진은 실제로 380×380인데 JSON의 해상도 표기는 달랐습니다.
> 이런 차이는 자동으로 고치지 않고 먼저 확인할 사항으로 남겼습니다.
> 학습 1,971장, 검증 805장, 시험 1,033장을 고정하고 63장은 별도 보관했습니다.
> 촬영일은 나눴지만 식물 고유 ID가 없어 식물 단위 독립성까지 보장하지는 못합니다.”

**조작자:** 네 숫자를 차례로 짚는다. 별도 보관은 삭제가 아님을 보여준다.
이 화면을 앱의 자동 데이터 분할 기능이라고 소개하지 않는다.

### 3. 전이학습과 실제 배포 추론 — 1:25~2:40

**화면:** 결과 표 → AIStream 서빙/API 테스트.

**발표자**

> “기존 녹차 모델의 특징 추출기는 고정하고 마지막 주차 분류층만 추가 학습했습니다.
> 시험 자료에서 제공 라벨과 일치한 사진은 1,024장에서 1,025장으로 한 장 늘었습니다.
> 큰 개선이라고 말하기보다, 학습한 모델을 다시 배포해 호출할 수 있는지 확인했습니다.”

**조작자:** 준비한 사진을 `POST /predict`에 넣고 실행한다.

**기대 관찰:** HTTP 200, 주차 3. 사전 확인에서 신뢰도는 0.641636이었다.
응답 지연은 실행 때마다 달라질 수 있다. 사전 확인 한 번은 약 1.02초였다.

**발표자**

> “이 사진의 제공 라벨은 3주차입니다.
> 저장된 비교 결과에서 기존 모델은 2주차, 추가 학습 모델은 3주차로 예측했습니다.
> 지금 배포된 API의 응답도 3주차인지 확인하겠습니다.
> 이 사진은 이미 비교에 사용한 사례이므로 새로운 독립 성능 시험은 아닙니다.”

API 결과가 기대와 다르면 그대로 설명하고 저장된 실험 결과와 구분한다.
신뢰도 0.641636을 “정답일 확률 64%”로 해석하지 않는다.

### 4. 모델을 정답 대신 검수 근거로 사용 — 2:40~3:40

**화면:** 로컬 비교 이미지와 보고서의 불일치 설명.

**발표자**

> “남은 불일치 8장은 모두 2024년 8월 3일 사진입니다.
> 제공 라벨은 1주차인데 모델은 4주차라고 했습니다.
> 학습에 쓰인 1주차 사진과 배경·화분 구성도 다릅니다.
> 모델이 배경에 영향을 받았을 수도 있고, 촬영이나 기록을 확인해야 할 수도 있습니다.
> 사진만으로 어느 쪽이 틀렸다고 단정할 수는 없습니다.
> 그래서 4주차로 자동 수정하지 않고, 원본 재배 기록을 확인할 검수 후보로 남깁니다.”

**조작자:** 불일치 묶음과 비교 사진을 가리킨다. 다른 작물로 바꾸거나
현장에서 시험 자료를 학습에 다시 넣지 않는다.

### 5. 사람이 판단하고 다음 담당자에게 전달 — 3:40~5:10

**화면 전환 시 반드시 말할 문장**

> “여기까지는 실제 녹차 실험입니다.
> 지금부터는 합성 기록으로 구현된 검토·인수인계 흐름을 보여드리겠습니다.
> 앞의 실제 8장을 이 공개 앱에 연결한 상태는 아닙니다.”

**조작자**

1. 공개 앱에서 후보 기록 하나를 열고 실제로 표시된 후보 이유와 원문을 읽는다.
2. `보류` 탭에서 다음을 입력한다.
   - 이유: `현재 자료만으로 후보 원인을 확정할 수 없어 원본 확인이 필요함.`
   - 다음 조치: `원본 기록 작성자에게 값과 단위의 근거를 확인하고, 확인 자료를 첨부해 재검토.`
3. 저장한 뒤 `보류` 상태를 보여준다. 근거가 없으므로 해소하지 않는다.
4. 그 기록을 선택해 인수인계 스냅샷을 생성하고 HTML 또는 JSON을 내려받는다.
5. 내려받은 파일에서 미해결 상태, 보류 이유, 다음 조치를 보여준다.

**발표자**

> “봤다는 표시와 문제가 해결됐다는 표시는 다릅니다.
> 판단 근거가 부족하면 보류하고, 무엇을 확인해야 하는지 남깁니다.
> 인수인계는 그 시점의 내용을 고정해서 전달합니다.
> 실제 녹차 불일치 후보에도 이런 검토 이력을 연결하는 것이 다음 구현 단계입니다.”

이 장면에서 보정·해소·재학습까지 억지로 이어가지 않는다.
불확실한 건을 근거 없이 초록색으로 바꾸지 않는 것이 시연의 핵심이다.

**발표자**

| 서빙이 유휴 중지됨 | 현재 설정은 유휴 60분이다. 시작 전에 상태를 확인하고 플랫폼의 정식 재개 절차를 따른다. 기존 공용 서비스 설정은 바꾸지 않는다. |

| 공개 앱에서 저장 충돌 | 최신 기록을 불러와 초안을 확인한다. 저장 성공 여부를 확인한 뒤 인수인계를 만든다. |

| 발표 시간이 3분으로 줄어듦 | 문제 30초 → 실제 API 45초 → 불일치 8장 45초 → 합성 보류·인수인계 45초 → 정리 15초. |

## 예상 질문과 답변

**녹차밖에 안 되나요?**  
이번 추가 학습·평가는 녹차만 했습니다. 다른 작물은 각 작물의 데이터와 모델로 별도 검증해야 합니다.

**정확도가 99%인데 왜 필요한가요?**  
이번 수치는 제공 라벨 기준 일치율입니다. 1주차 재현율은 57.89%이고,
기존 모델이 이번 시험 사진을 사전학습에서 봤는지도 알 수 없습니다.
전체 점수만으로 사용 범위를 결정하기 어렵다는 사례입니다.

**8장은 잘못된 라벨인가요?**  
아직 모릅니다. 모델과 라벨이 다르다는 사실만 확인했습니다.
재배 시작일·촬영 기록 등 독립 근거를 확인하기 전에는 원본 라벨을 유지합니다.

**검수해서 성능이 좋아진 건가요?**  
아닙니다. 이번에는 원본 라벨을 수정하지 않았습니다.
한 장 개선은 추가 학습 결과이며 검수 효과는 후속 실험 대상입니다.

**앱에서 보정하면 바로 재학습되나요?**  
아닙니다. 현재 검토·보류·보정·인수인계와 학습 실행은 분리돼 있습니다.

**지금 배포된 모델은 검증된 파일과 같은 버전인가요?**  
현재 서빙은 등록 v1이며 실제 사진 응답을 확인했습니다.
별도로 내려받은 등록 v2는 10개 파일 모두 로컬 학습 번들과 해시가 일치했습니다.
v1과 v2의 파일 동일성까지 확인한 것은 아닙니다.
